## 1. PROBLEMS TO SOLVE (already diagnosed — verify each yourself before changing code)

### Item 1 — Kannada text is broken / not understood by the model
Diagnosed causes:
1. `main.py` Kannada glossary (`kannada_map`) is applied in dict order with `str.replace`, so short keys fire before longer phrases that contain them. Example: `ಮುಂಗಡ` replaces first, so `ಮುಂಗಡ ಹಣ ಮರುಪಾವತಿ ಹಕ್ಕು` is left half-translated. Same for `ಅವಧಿ` vs `ಪ್ರೊಬೆಷನರಿ ಅವಧಿ`, `ಬಾಡಿಗೆ` vs `ಉಪ ಬಾಡಿಗೆ`. Fix = apply keys sorted by length, longest first.
2. `server/controllers/aiController.js`: `extractText` OCRs with `'eng+kan'`, but `reprocessDocument` uses `'eng'` only (two places). Reprocessed Kannada scans become garbage. Also no `langPath` is configured for the `kan.traineddata` shipped in `server/` (check the installed tesseract.js version and how it loads languages before deciding whether to wire it; if wiring is risky, leave the default behaviour and document it).
3. Translation failure is silent and destructive: if Google Translate errors or is rate-limited, the raw Kannada chunk is kept and then Stage 2.5 deletes ALL remaining Kannada (`re.sub(r'[\u0C80-\u0CFF]+', '', ...)`). The model receives empty/partial text and nobody is told.
4. Translation chunks are cut every 1000 characters regardless of sentence, line, or redaction-placeholder boundaries and are joined with `''`. This can split `[AADHAAR_REDACTED]`-style placeholders and lose line breaks/numbering that clause parsing needs.
5. Stage 0 regexes use `\s+`, which also matches newlines, so they can glue words across lines.
6. Likely (confirm with a test, do not assume): many Kannada PDFs use legacy fonts (Nudi/Baraha). PyMuPDF returns garbled Latin-looking text for these, which passes the current "text density" check. Garbled extraction should be detected and routed to OCR.

### Item 2 — Only 3–4 clauses get highlighted in English documents
Two separate causes:
A. SEGMENTATION. `parse_legal_structure()` only splits on `\n N. Heading`. It first tries an ALL-CAPS heading regex and only falls back to the generic regex if the caps regex matched ZERO times. On a mixed-case 6-clause contract, only clauses 1-3 are found and clauses 4-6 (including non-compete and termination) are merged into clause 3. Formats such as `1)`, `(1)`, `Clause 1`, `Article I`, `Section 5`, `1.1`, `(a)/(i)` sub-items, `WHEREAS` recitals, `SCHEDULE/ANNEXURE`, and "number alone on its own line" (common PDF output) are not recognised and fall back to blank-line paragraphs. Also `clauseIndex` is taken from the document's own number, and `clause_analyzer` keys results by `clauseIndex`, so duplicate numbers (two lists both starting at "1.") would silently overwrite each other.
B. DETECTION COVERAGE. `rule_engine.py` has ~5 risk rules, mostly employment. Rental/NDA/vendor/criminal-adjacent clauses fall through to RAG; the knowledge base is only ~16 chunks / 9 acts; `validate_authority_strength()` then short-circuits weak matches to `NO_ISSUE_DETECTED`; and `heuristic_grounded_evaluation()` only recognises governing-law and indemnity. Note also that `red_flag_terms` contains the substring `"bar"`, which matches words like "embargo"/"barrier". The classifier only knows 5 domains, so criminal-adjacent documents end up "Unclassified" and RAG gets no domain filter. `doc_state` is taken from the first clause only.

### Item 3 — No one-sided test documents
Existing test texts (see `DOCUMENT_UPLOAD_SPECIFICATIONS_AND_GUIDELINES.md` scenarios A–D and `scratch/test_phase5_clause_analysis.js`) are mostly balanced and tiny (about 6 hand-written clauses). `COMPREHENSIVE_VERIFICATION_REPORT.md` claims 100% accuracy, but that rests on those few clauses. We need a labelled synthetic corpus of heavily one-sided agreements plus balanced controls, and an evaluation harness.
